# Frostveil L3: read-only modpack verification

L3 adds scoped file verification, plugin activation/order evidence, offline server profile comparison and a future update preview. It never downloads mod assets or writes to Skyrim, SKSE, SkyMP, load order or world data. Launcher version is 0.1.2; existing installer/application/user-data identities remain intact. L1 Play stays gated by the existing local runtime baseline. L2 updater and its signing gates are separate.

## Reuse and pinned SkyMP evidence

Reuse: `installation.ts`, discovery/version probes, `files.ts` path safety, streamed hash concepts, existing PackManifest V1 field names, backup, typed preload/IPC, React Updates area and L2 self-updater. New focused modules are in `src/main/modpack/` and `src/renderer/ModpackPanel.tsx`.

SkyMP engine commit `2849e676fe008925384b26f34476e382a30bd877`, working checkout `5397cd3bf4666c942f78193107881d8cf0ac2748` (existing develop baseline):

- `skymp5-server/ts/settings.ts`: dataDir/loadOrder settings, additional sources and configuration merging. The exporter does not execute this service; unresolved additional sources are refused.
- `skymp5-server/ts/manifestGen.ts`: generated loadOrder plus plugin/BSA filename, size and signed CRC32; `.esm/.esp` naming accepted, `.esl` rejected by its BSA-name helper. Existing manifest is an input, not regenerated by L3.
- `libespm/src/Loader.cpp`, `Combiner.cpp`, `TES4.cpp`: full plugin index mapping and required MAST relationships. No verified FE/light mapping was found in the inspected pinned path.
- `skymp5-client/src/services/services/loadOrderVerificationService.ts`: Game.getModCount/getModName, required server prefix checked by filename/size/CRC32. More client mods produce a warning. Existing SkyMP checks remain intact.
- Archives serve compiled Papyrus requirements; a server archive list alone does not define all required client assets.

The [upstream configuration reference](https://github.com/skyrim-multiplayer/skymp/blob/main/docs/docs_server_configuration_reference.md) describes dataDir, loadOrder, archives and generated manifest. Its current branch is background documentation; local source decides L3 coverage.

## V1 contract and limits

`PackManifest` retains `schemaVersion`, `packVersion`, `channel`, `minimumLauncherVersion`, `requiredSkyrimRuntime`, `requiredSKSEVersion`, `requiredSkyMPClientVersion`, `files` and file path/hash/size/component/ownership/permission fields. It adds pack/profile identity, timestamp, components with dependency DAG, plugin requirements, explicit distribution/signing metadata and `skyMPClientRequirements`. Early L1 placeholder manifests missing the extended mandatory fields are rejected; they were never installed or production distributed.

Schema is exact: unknown keys, missing fields, unsafe paths, case-insensitive collisions, duplicate IDs/orders, invalid hash/size/version, cycles, missing masters and contradictory roles fail validation. A component can have multiple files. Native/shared/client-only/runtime/visual/developer/authorized third-party/external categories are distinct. Native/Bethesda/SKSE/external assets cannot be marked redistributable. Third-party distribution requires explicit permitted ownership and permission metadata; legal verification remains a publishing prerequisite.

- Manifest/profile JSON: 4 MiB; remote signed envelope: 6 MiB; up to 10,000 files, 2,000 components, 254 plugin identities.
- Verification file size: up to 32 GiB, streamed 256 KiB chunks, two workers by default and at most four. Metadata files are bounded separately. Hash verification runs fresh, without mtime-only READY caching.
- Only scoped native executable/SKSE files and explicit Data subtrees/extensions are accepted. No arbitrary saves/system paths, ADS, traversal, drive/UNC targets, redirected links/junctions or unknown executable invocation.
- Five required SkyMP identities must refer to the actual loader targets: MpClientPlugin.dll, SkyrimPlatform.dll, SkyrimPlatformImpl.dll under `Data/Platform/Distribution/RuntimeDependencies`, client JS and runtime-matching versionlib database. Matching names in another folder do not pass. Every identity is linked to required hashes, not inferred from the L1 baseline's client label.
- Resource versions use four numeric fields, e.g. SKSE `0.2.2.6`. Pack/launcher/server profile versions use semver. Content mismatch alone is `modified`; `outdated` requires actual older resource version evidence.

Synthetic complete fixtures live in `tests/pack-fixture.ts` and smoke/test code. No real game/config hashes or local profiles are packaged or committed.

## Offline development profile

The main process reads only `modpack-development.json` under its existing launcher-private data directory. Shape: `{manifest, server}`. It must be explicitly `local-development`, is always labelled **LOCAL DEVELOPMENT ONLY**, and never counts as publisher-authenticated. Its source is developer controlled; the renderer cannot choose a path, URL, trust key or enforcement setting.

`scripts/export-modpack-profile.mjs` accepts explicit local settings, the existing generated SkyMP manifest, an explicit client-requirements manifest and pinned engine commit. It checks plugin order/size/CRC32, streams fresh SHA256 and parses bounded TES4 headers. Output is a whitelist of profile/pack/runtime identities, plugin order/hash/size/CRC/masters, archive basenames, timestamps and limitations. No raw config, masterKey, credentials, endpoints, absolute paths, player data or server directory structure is exported. The profile expires within seven days. Output is limited to launcher-private `.local` or user-data metadata, outside the server.

```powershell
node scripts/export-modpack-profile.mjs --settings <local-settings-json> --manifest <existing-plugin-manifest-json> --requirements <explicit-development-requirements-json> --output .local/modpack-development.json --engine-commit <pinned-40-character-commit>
```

Do not publish these local inputs/output. No new endpoint or distribution repository exists. Offline export is not a live running-server measurement. A missing profile shows SERVER PROFILE NOT CONFIGURED.

## Trust and remote interface

Modpack signatures use Node crypto Ed25519 over the exact payload bytes containing both manifest and server profile. Envelope key ID must match the signed manifest. Publisher keys are pinned in controlled main-process configuration; production keys/source are currently absent. Private signing keys exist only as clearly synthetic deterministic test inputs, never as a production trust root.

Future approved remote source: fixed GitHub Release JSON URL, HTTPS, manual redirects, one allowed redirect to the exact `release-assets.githubusercontent.com/github-production-release-asset/...` host/path class, no second/unapproved redirect. Bounded response and timeout; signature is verified before parsing trusted requirements. Missing key, unsigned/tampered payload, unavailable network and invalid profiles fail closed. Test transport is simulated; no real production source has been configured or fetched.

SHA256 authenticates file integrity only. L2 `latest.yml`/Authenticode and modpack signatures use different trust/version domains. No asset fetch or install API exists in L3.

## Order evidence and compatibility limits

Read-only configuration evidence uses known implicit official masters, physically present Skyrim.ccc entries and `plugins.txt` activation markers. Non-implicit active plugins need corroborating `loadorder.txt`; absent, empty, partial or conflicting lists stay UNVERIFIED. No arbitrary directory enumeration supplies order. Parser reads TES4 flags and MAST relationships; malformed/compressed/unsupported header fields fail conservatively.

Shared full plugin indices must match the server prefix. Client-only full/light extras after that prefix need no server asset. Required `.esl`/ESL-flagged shared plugins stay UNVERIFIED for this pinned SkyMP. Obvious MO2/usvfs/Vortex markers, redirected files or ambiguous master-first reordering prevent a verified runtime-view claim. Marker detection is partial: direct physical SKSE configuration evidence never proves the actual loaded order of a running game or every mod manager configuration.

Six compatibility outcomes: Compatible, Update Required, Incompatible, Unverified, Not Configured, Scan Error. Required runtime, client native hashes, files, activation, dependencies, plugin prefix and matching fresh server/profile/pack identity are needed. Local file verification, offline snapshot compatibility and live server version are displayed separately. Live server is always UNVERIFIED in L3.

Future plan items describe expected/observed evidence, required/optional policy, eligible size and possible manual/managed resolution. Modified/user-owned conflicts require review, external files require manual verification. No unrelated-mod deletion is planned, and no plan is executed. L4 still needs approved distribution rights/assets, immutable signed profiles, production key/rotation policy and approved source.

## UI and policy

Updates contains Scan Modpack, progress/cancel, component/file/plugin details, diagnostic reasons and future plan. Strings render as React text with Thai/Unicode support. No INSTALL/UPDATE MODPACK button or second window. Cancel is validated by the existing sender/frame checks and can run while the scan owns the mutation lock. Cancellation clears previous success; selecting a folder invalidates results.

`mandatoryPackPolicy` defaults OFF in main code. Enabling it later requires an authenticated compatible profile, and Play rescans before the launch decision. Renderer/settings/manifest cannot override this gate. An unconfigured L3 does not block the current verified L1 Play path.

Run `npm run typecheck`, `npm test`, `npm run package:nsis`, `node scripts/verify-artifacts.mjs`, `npm run smoke`, then packaged smoke with `LAUNCHER_SMOKE_EXE`. CI discovers all `tests/*.test.ts`; it performs fixture-only packaged checks and never scans a developer's real installation. No L3 source push or Release is authorized by this task.
